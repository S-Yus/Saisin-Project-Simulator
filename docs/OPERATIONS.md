# 公開構成と運用手順（起動・開催・停止・更新・削除・障害復旧）

## 1. 構成
- **Node.js 24.11.1（固定）＋単一プロセス＋永続ディスク上の SQLite（WAL, synchronous=FULL, secure_delete=ON）**。`node:sqlite` を使用（Node 24.11.1 で動作確認済み。Node 24 では実験的機能のため起動時に警告が出る。これは消さずに残している）。本番・確認用環境では、固定版以外の Node では起動しない（`ALLOW_UNVERIFIED_NODE=1` で解除可能だが非推奨）。
- **単一プロセス制約**: 書込みの直列化と終了判定の一貫性をプロセス内のトランザクションに依存するため、同じDBに対してアプリを複数起動・複数台構成にしない。削除用の単独スクリプト（`scripts/purge.js`）だけは同じDBに同時アクセスしてよい（SQLite のロックで直列化）。
- 公開経路: インターネット →（443/TLS）リバースプロキシ → 127.0.0.1:8080 のアプリ。アプリの待受ポートを外部に公開しない。管理画面・管理API（`/admin*`, `/admin-api/*`）はプロキシで許可IP（拠点・VPN）に限定する。設定例: `deploy/Caddyfile.example`, `deploy/nginx.conf.example`。
- 環境の分離: `APP_ENV=staging`（確認用環境）と `APP_ENV=prod`（本番）は、別プロセス・別DB（別ボリューム）・別トークン・別ドメイン。どちらも本番形式データのみ受け付ける。**確認用環境は、さいしんが動作確認を行うための環境**で、確認の前に動いている必要があるため、利用許諾が未確認・取引条件が仮設定・動作確認が未記録のままでもデータの固定と公開ができる（参加者画面の最上部に「確認用環境（動作確認用）。本番ではありません」と未確定事項を常に表示）。**本番だけ**が、許諾の確認・条件の確定・仮設定の解除・動作確認の記録を公開の条件にする。確認用環境のURLは確認に関わる人だけに伝え、説明会の参加者には配らない。開発・検算は `APP_ENV=dev`（赤帯表示。**ループバック（127.0.0.1）でのみ起動でき、外部に公開できない**。架空データのほか、許諾未確認の実データをローカルの検算用に扱える）。
- 再現可能な起動: `Dockerfile`（node:24.11.1-bookworm-slim、非root、/data ボリューム、HEALTHCHECK）、`deploy/docker-compose.yml`（staging/prod/削除ジョブ）、Docker を使わない場合は `deploy/systemd/`。**この開発端末には Docker がなく、イメージのビルドは未検証**。
- 秘密情報: `.env.example` を元に環境ごとの `.env.staging` / `.env.prod` を作る（リポジトリに入れない）。トークンは `openssl rand -hex 32` 等で生成した32文字以上・互いに異なる値。

## 2. 管理トークンの扱い（共有トークン方式を維持する条件）
- トークンは HTTP の `Authorization: Bearer` ヘッダーでのみ受け付ける（URL・クエリ・Cookie では受け付けない）。
- 管理画面はトークンを**メモリ上の変数にのみ**保持（localStorage/sessionStorage/URL に保存しない。再読み込みで再入力）。HTML/JS にトークンは埋め込まれていない（テストで確認）。
- アプリのログは「メソッド 経路 状態 所要時間」のみ（トークン・参加者ID・IP・参加コードは出力しない。テストで確認）。プロキシのログもクエリと Authorization を記録しない設定にする。
- 認証失敗は送信元IPあたり1分10回で一時拒否（プロキシ配下では `TRUST_PROXY=1`）。前提として**管理画面はIP制限下でのみ公開**する。担当者ごとの識別・多要素認証は未実装（`admin_audit` は役割単位で記録）。

## 3. 起動・停止・更新・復旧
| 作業 | Docker | systemd |
|---|---|---|
| 起動 | `docker compose -f deploy/docker-compose.yml up -d staging` | `systemctl start nisa-sim@staging` |
| 稼働確認 | `curl -s https://staging.example.jp/healthz` → `{"ok":true}`、起動ログの `node=v24.11.1 app=… spec=… code=…` | 同左 |
| 正常停止 | `docker compose … stop staging`（SIGTERM → 新規受付停止 → 処理中のリクエスト完了 → DBクローズ、最大10秒） | `systemctl stop nisa-sim@staging` |
| 更新 | ①説明会の開催時間外に行う ②新しいイメージをビルド ③停止 → 起動 ④管理画面で「実行コード」ハッシュが変わったことを確認 ⑤**コードが変わると動作確認は自動解除**されるため、確認用環境で再確認 → 本番で確認を記録し直す | 同左 |
| 障害復旧 | 再起動で復旧（コミット済みの注文・進行は失われない。未コミットのものは「未受付」になり、参加者画面の「受付状況を確認」で判別できる） | 同左 |
| 削除ジョブ | アプリ内で起動直後＋1分ごと。アプリ停止中も期限どおりに削除するには `prod-purge`（compose）または `nisa-sim-purge@prod.timer` を有効化 | 同左 |
※ Windows の開発端末では SIGTERM による正常終了の動作は確認できていない（Linux コンテナ／systemd での確認が必要）。

## 4. 開催回ごとの流れ
1. **確認用環境に載せる**: `npm run build-data` で取込ファイルを生成（検証エラーがあれば生成されない）→ 確認用環境の管理画面で取込 → 固定（未確定事項が残っていても固定できる。残っている項目は画面に表示される）
2. 確認用環境で開催回を作成（日時・人数・期間・初期資金・追加資金）して公開。**この時点でさいしんがURLを開いて操作できる**
3. **さいしんの確認担当が docs/CHECKLIST.md を実施**（自動テスト合格は確認の代わりにならない）。指摘があれば台帳（`market-data/catalog.json`）や設定を直し、1〜2をやり直す（確認用環境の開催回は何度でも作り直せる）
3a. **確定値を反映する**: 利用許諾の確認が取れた出典を `license_status: confirmed` に、さいしんが確認した取引条件を `terms_status: confirmed`、基準を `status: confirmed` にして取込ファイルを作り直す。確認用環境に取り込み直し、開催回の「仮設定」を外して、最終の値で動くことを確かめる
4. **本番に載せる**: 3aと同じ取込ファイルを本番に取込 → 固定（未確定事項が残っていると本番は固定を拒否する）→ 同じ設定の開催回を作成して「仮設定」を外す → 管理画面の「構成指紋」が確認用環境（3aの最終状態）と一致することを確認 → 確認担当が確認担当トークンで本番に確認を記録 → 運用担当が公開
5. 会場にQR（管理画面の「参加用QRコード」→「会場用に大きく表示」で全画面表示・印刷）を掲示。QRに入るURLは環境変数 PUBLIC_URL（例: https://staging.nisa-simulator.app）。未設定で管理画面を 127.0.0.1 から開くと、そのPCでしか開けないQRになり、警告が出る。確認用環境は node ops/make-qr.js で data-staging/join-qr.svg にも書き出せる。開始時刻前は参加不可、終了時刻にサーバーが全操作を拒否
6. 開催中: 全体の一時停止／再開、異常時は緊急停止（元に戻さない運用）
7. 再開催は**新しい開催回**を作り、再度確認する

## 5. 終了・削除
- 終了時刻（サーバー時刻）以降、既存セッションを含め参加者のすべての操作・データ取得を 410 で拒否。端末の時計を変えても延長できない。開いたままの画面は次の通信・30秒ごとの確認・画面復帰時に終了表示になり、端末のトークンを消去する。削除後はトークン自体が無効（401）。
- 参加者データは**終了時刻＋保持時間（既定24時間）**に削除（参加者・試行・保有・注文・受渡予定・台帳・積立・評価履歴・冪等記録）。市場データ・開催設定・確認記録・削除記録（件数のみ）は残す。
- 失敗時は全体をロールバックし `purge_log` に失敗を記録、次回再試行。管理画面に警告を表示。`scripts/purge.js` は失敗時に終了コード2（監視で通知）。
- 保持時間の変更は運用担当のみ、影響（新しい削除予定・対象人数）を確認してから。削除済みデータは延長しても復元しない。即時削除は開催名の再入力が必要。

### 論理削除と完全削除の区別（保証できる範囲）
| 範囲 | 状態 |
|---|---|
| アプリのDB上の行 | 期限後に削除（テストで確認） |
| DBファイル内の空き領域・WAL | `secure_delete=ON` で削除時に上書き、さらに WAL の切り詰めと VACUUM を実行（失敗しても削除自体は完了扱い） |
| ディスク・ボリュームのスナップショット、クラウドの自動バックアップ、ホスティング事業者の複製 | **アプリからは消せない。保証できない** |
| プロキシ・監視サービスのログ | アプリは参加者IDやトークンを出力しない。プロキシ側の設定に依存 |
| 端末の画面・スクリーンショット・ブラウザー履歴 | 回収できない |

24時間後の完全削除を求める場合の構成: ①参加者データを含むボリュームをバックアップ・スナップショットの対象から外す ②ボリュームを暗号化し、開催回ごとにDBファイルを分ける（終了後にファイルごと消去）③プロキシ・監視に参加者識別子を送らない。
**バックアップを無効化する場合の影響**: 開催中にディスク障害が起きると、その回の参加データは復旧できない（説明会は中断し、新しい開催回でやり直す）。市場データと設定は取込ファイル・手順から再作成できるよう、取込ファイルを別途保管しておく。

## 6. 更新とロールバック
- 更新前に、現在のコード一式（またはイメージのタグ）と `/whoami` の「実行コード」ハッシュを控える。DBファイルは開催時間外に停止した状態でコピーして退避する（参加者データを含む退避は、その開催回の削除予定までに消す）。
- 更新後に問題があれば、停止 → 控えたコード（イメージ）に戻す → 起動。スキーマの変更は列の追加だけで、古いコードでも同じDBを読める。
- コードを戻した場合も実行コードのハッシュが確認時と一致しなければ公開できない（一致すれば確認は有効なまま）。
- データの差し替えは、新しい取込 → 固定 → 開催回の作り直し（または参加者がいない回のデータ差替え）で行う。固定済みのデータは変更できない。

## 7. ログとバックアップの方針
| 対象 | 方針 |
|---|---|
| アプリのログ | 標準出力に「メソッド 経路 状態 所要時間」と起動・削除ジョブの結果のみ。保存期間はホスト側で設定（参加者を識別する情報は含まない） |
| プロキシのログ | クエリ文字列（参加コード）・Authorization・IPを記録しない設定にする（設定例のとおり） |
| DBのバックアップ | 参加者データを含むため、**既定では取らない**ことを推奨（取る場合は削除予定までに消える仕組みが必要）。市場データと設定は、取込ファイル（`market-data/`）と本手順から再作成できる |
| 監視 | `/healthz`、`scripts/purge.js` の終了コード（2＝削除失敗あり）、管理画面の削除記録 |

削除の実行目標: アプリ稼働中は1分ごと、停止中は独立ジョブの間隔（設定例は15分）ごとに判定するため、**削除予定時刻から最大でその間隔だけ遅れる**。失敗は `purge_log` に記録され、次の回で再試行される。

## 8. 負荷・容量
最大参加人数は開催回ごとに設定（超過は 429）。会場Wi-FiのNATで全員が同じIPになるため、参加のレート制限は送信元IPあたり毎分600（`JOIN_RATE_PER_MIN`）。測定結果は docs/TEST_REPORT.md。本番相当の環境で `node scripts/loadtest.js 300 60 session` を再実施すること（Linux・実ネットワーク・TLS経由は未測定）。

## 9. 確認用環境をこのPCから公開する（Cloudflare Tunnel。2026-11-23 設定）
`staging.nisa-simulator.app` を、このPCで動く確認用アプリ（127.0.0.1:8081）に向けるトンネル `nisa-staging` を作成済み。DNS（CNAME）も登録済み。
| 操作 | コマンド（`nisa-sim` フォルダで） |
|---|---|
| アプリを起動 | `powershell -ExecutionPolicy Bypass -File ops\start-staging.ps1` |
| 外部に公開（トンネル起動） | `powershell -ExecutionPolicy Bypass -File ops\start-tunnel.ps1` |
| 外部公開を止める | `powershell -ExecutionPolicy Bypass -File ops\stop-tunnel.ps1` |
| アプリを止める | `powershell -ExecutionPolicy Bypass -File ops\stop-staging.ps1` |
| 実データを入れ直して開催回を作る | `node ops\seed-staging.js 14`（数字は開催日数。参加コードは `data-staging\join-code.txt`） |

- 参加URL: `https://staging.nisa-simulator.app/?code=<参加コード>`。管理画面はこのPCのブラウザーで `http://127.0.0.1:8081/admin`（トークンは `.env.staging`）。
- 管理画面・管理API（`/admin*`, `/admin-api/*`）は外部に出していない。二重に遮断している: ①トンネルの設定（`ops/cloudflared-staging.yml`）で該当の経路を404にする ②アプリの `ADMIN_LOCAL_ONLY=1`（`.env.staging`）で、プロキシ／トンネル経由の要求には管理系の経路を404で返す。①だけでは `/x/../admin` のような書き方ですり抜けたため②を追加した（2026-11-23、外部URLから `/admin`・`/admin.js`・`/admin-api/*` と経路の書き換え6通りがすべて404、このPCからは開けることを確認）。
- **PCの電源が入り、アプリとトンネルの両方が動いている間だけ**使える。再起動後は上の2つの起動コマンドを実行する。スリープすると外部から開けなくなる。
- **トンネルは外向きの TCP/UDP 7844 番ポートを使う。** 7844番が閉じられたネットワークでは接続できない（2026-11-23、Wi-Fi「SRAS5G」で接続不可、別の回線で接続できることを確認）。その場合は自宅回線やテザリングなど別の回線で起動するか、常時稼働のサーバーに設置する。ネットワークの制限を回避する設定は行わない。
- 秘密情報: `.env.staging`（管理トークン）、`%USERPROFILE%\.cloudflared\`（トンネルの資格情報）。共有・公開しない。
